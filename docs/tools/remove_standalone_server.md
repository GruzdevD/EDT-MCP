# remove_standalone_server

Remove the WST STANDALONE-server wiring that makes an EDT project treat an infobase as an autonomous server, so a NORMAL infobase application can be created for it. A base wired as a standalone server is surfaced by the server provider, never as a plain type.infobase app. Destructive (deletes the standalone server + config), two-phase with confirm; the served DATABASE is never touched. Parameters and examples: get_tool_guide('remove_standalone_server').

## Guide
Removes the WST STANDALONE-server wiring that makes an EDT project treat an infobase as an autonomous (standalone) server — the inverse of binding a base as one. Destructive, two-phase with `confirm`; the served DATABASE is never touched.

Why it exists: a base that a project's config registers as an autonomous server is surfaced by the WST-server application provider (the standalone-server feature), NOT by the normal infobase provider. While that wiring stands, no normal `com.e1c.g5.dt.applications.type.infobase` application can materialize for the base (regardless of `create_project_application` / `create_infobase`). Deleting those standalone servers rolls the base back to a plain file infobase, after which a normal application can be created.

## Parameter details

- **projectName** (required): the EDT project whose standalone-server wiring for the infobase to remove.
- **infobaseName** (required): the name of the infobase (from `list_infobases`) whose standalone-server wiring to remove.
- **confirm** (boolean, default false): `true` deletes the standalone server(s) and cleans the registry; `false`/omitted previews only (what would be removed + the full list of servers EDT currently knows).

## Result

JSON with `success`, `project`, `infobaseName` and:
- on a **preview**: `confirmationRequired: true`, `matchedServers` (what the removal targets), `allServers` (everything EDT knows — evidence/diagnosis), `message`.
- on a **removal**: `removedServers` (each with `name`, `serverName`, `infobaseId`, `cleanup`), `remainingServers` (servers still present), `message`.

## Typical usage

```
# 1. Preview what backs the base "Инвест" (no side effects).
remove_standalone_server  projectName="mom"  infobaseName="Инвест"

# 2. Delete the wiring so the base becomes a NORMAL infobase.
remove_standalone_server  projectName="mom"  infobaseName="Инвест"  confirm=true

# 3. Create a NORMAL application over the base.
create_infobase  projectName="mom"  mode=register  infobaseName="Инвест"  applicationKind=infobase
```

## Gotchas

- **The DATABASE is never touched.** Only the WST standalone-server registration and its config entry are deleted. The base files remain intact.
- **This is the prerequisite for a normal app when a base is wired as an autonomous server.** Until the wiring is removed, the base stays server-surfaced and a `type.infobase` application cannot surface.
- **Two-phase on purpose.** Run it without `confirm` first — the preview lists exactly what will be deleted. Confirming deletes.
- **Registry cleanup is best-effort** — if the `infobases.yaml` entry cannot be removed (reported as `cleanup: FAILED`, one per removed server), it self-heals on EDT restart.
