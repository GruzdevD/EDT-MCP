# Design

## Context

На `8a9e5103` `ProjectSourceManifest` уже различает HEAD/index/disk, `ProjectCommitPlan` вычисляет дерево поверх ожидаемого родителя, `ProjectCommitExecution` защищает обновление ref и индекса, а `SnapshotYaxunitRunner` собирает удержанный дисковый payload. Связать следует **идентичности входов** этих операций: успешное выполнение одной не свидетельствует об успешном выполнении другой. Snapshot живёт 10 минут; plan — до 5 минут и не дольше snapshot; обычный commit receipt — 10 минут. Они не годятся на роль журнала change.

Источник проверок — харнесс `a1f5d759`: `content/commands/1c-dev-build.md:554–584` (metadata/index), `:891–905` (первый красный), `:994–1051` (BASE, периметр, порядок фаз), `:1237–1258` (независимый запуск, версии методов), `:1326–1345` (публикация отчёта). Паритет pre-pass — `content/tools/bsl-prepass.sh` и `tools/test-bsl-prepass.sh`; UUID и СКД — `edt-uuid-check.sh` и `dcs-check.py`.

## Goals / Non-Goals

**Goal:** новый клиент с теми же полномочиями находит проверяемые факты по `repoId/changeId/cycle`: документы, выбранные версии, входы, jobs, plan и результат записи. Для проверки не требуются клон, копия дерева, общий Git-инструмент или shell хоста.

**Non-goals:** EDT-MCP не выбирает тестовое покрытие, не присваивает APPROVE, не ведёт budgets, locks и сессии агентов, не выдаёт согласие от имени владельца. Live debug и live EDT diagnostics сохраняют собственную семантику: `unknown` или снимок по времени не доказывают соответствия модели дереву. Требующая такого соответствия проверка без доказательства останавливается. Источник дизайна — уже существующий change; archive и публикация ветки не входят в этот маршрут.

## Decisions

### 1. Один идентификатор — одна неизменная версия

Тип версии различает `snapshotId + side`, `planId + treeId`, `commitSha + treeId` и `baselineId`. Git object ID с указанием алгоритма не смешивается с digest сырых байтов или digest манифеста. Определение полного SHA по ветке выполняется один раз в начале чтения. Клиент получает server-issued `fileId` из манифеста либо поиска, включая неизменённые пути. Идентификатор — ссылка, а не полномочие.

| Операция (новые имена — проект контракта) | Вход и выход | Допуск, предел, отказ |
|---|---|---|
| `resolve_project_review` | repo/branch/change, ожидаемый final при наличии → наблюдаемый HEAD, design/build SHA с родителями и деревьями, BASE, per-commit и range handles | Только достижимая история разрешённой ветки. Разбирать `[ticket] dev-build <change>` и legacy `ticket: dev-build <change>` по точному change, сверять с известными receipts. История сверх бюджета или неоднозначное происхождение → incomplete/ambiguous, не последний parent |
| `inspect_project_version` | version, область, `manifest/diff/content/literalSearch`, fileId или литерал, диапазон/cursor → строки или байты, hunk/side/path, content ID, coverage/continuation | Права по repo/project и типу содержимого, привязанный к версии cursor. Лимиты выдачи/поиска/файла; выход за hard limit → причина, не пустой diff. Для периметра разрешения на корневые CI и settings задаются отдельно |
| `stage_verified_entries` | исходный snapshotId и явные entryIds одного repo → parent, index/disk IDs выбранных версий, receipt | Отдельный branch-scoped grant на stage. Повторно проверить избранные версии и отсутствие удалённых путей под защитой источников и блокировкой индекса. Отказ без частичной записи при конфликте, partial staging, diverged, смене HEAD. После изменения индекса нужен свежий снимок для дальнейшего preview |
| `preview_project_commit` в режиме build | исходный snapshot, entryIds, точные artifact revisions, message, change, список закреплённых проектов → прежний план плюс `candidateInputsId`, состав и срок | Одно изменяемое дерево, прежние ограничения репозитория, права отдельно на документы и запуск. Дерево, в котором не хватает обязательного дескриптора, не получает пригодные build inputs |
| `run_yaxunit_tests` | взаимоисключающие источники: прежний snapshot, `candidateInputsId` или commit с разрешённым scope; селекторы, опциональный цикл удержания → jobId, источник, манифест, отчёт | Те же execution grants на все проекты, bounded worker/deadline и отдельная ИБ; не смешивать с live launch/debug/update. Pending опрашивается `get_job_status`; новая подача — независимый запуск или busy |
| `inspect_change_evidence` | repo/change/cycle и kind → индекс разрешённых baseline/job/plan/receipt; baseline + target → сравнение production/tests/нормативных редакций | Read-only по субъекту/области, bounded pages до объявленного срока. Отказ в чтении, неполные данные и истечение срока отличимы от отсутствия изменений |
| `read_change_artifact` / `write_change_artifact` | list/read по change/kind/revision; put/create/append по ожидаемой редакции и ключу операции → точная revision, digest, Git blob ID, receipt | Отдельные read, write и append grants. Фиксированный реестр типов/вложенных capability IDs, лимиты документа и пакета. Immutable boundary — только create. Конфликт редакции не разрешать автоматической перезаписью |

Для server-side policy использовать действующий защищённый Windows-маршрут, закреплённые расположения и handle-based открытие. Ни `repoId`, ни поле capability не являются путём ОС. Для Git исключить внешние filters/hooks, символические ссылки и переходы между репозиториями. Лимиты страниц, scanned bytes, commits и TTL публикуются в capability metadata; ошибка квоты сообщает предел и допустимое продолжение, не host path. В trace/audit сохранять тип операции, результат, роль и счётчики, не тексты модулей, отчётов и токены доступа.

### 2. Проверять выборку на базе, а не совпадение двух SHA верхнего уровня

Перечислить дерево `parent + selected entries`, включая удаление и обе стороны rename; неизменяемый кандидат можно материализовать из snapshot и родителя до существования commit object. Build manifest перечисляет пути, фактические байты (digest/size), дескрипторы, кодировки, идентичность и порядок base/extensions; отдельно — seed digest, toolchain и профиль поддерживаемой сборки. Зависимости других repo читаются по явно закреплённым SHA. Ни один fallback к WT не разрешён. Если дисковая job имеет доказуемо равные полные входы, среду и selectors, допустимо сослаться на неё как на проверку кандидата **до commit**; независимое ревью всё равно запускает новую job по финальному SHA.

Для промежуточной metadata-границы выбрана реальная узкая запись в index: виртуальная выборка проще, но не доказывает требуемое харнессом `index=verified WT`. Stage не заменяет preview, не создаёт commit и не берёт объекты из общего индекса для финального дерева. Перед confirm владелец видит parent/tree/message/entries и связанные evidence. Передача `planId` не расширяет согласие; при истечении плана нужен новый preview с повторной сверкой состава и согласием. Выданная раньше job не оживляет старый план.

### 3. Сохранить эталон до того, как станет известен исход запуска

При старте цикла зарезервировать закрытую серверную запись `(owner, repoId, changeId, cycle, jobId)` и закрепить необходимые байты/деревья и ожидаемые ревизии документов. Не допускать двух конкурирующих стартов, претендующих на один первый результат. Завершение FAILED/BROKEN атомарно превращает резерв в immutable baseline с outcome/phase, доступным отчётом и manifest. При успешном первом запуске сохраняется outcome; он не создаёт ложного red baseline и не мешает позднему первому падению. При неизвестном исходе после сбоя — явная неопределённость и восстановление, не реконструкция из текущего WT. Разделение тестовых и продуктивных файлов опирается на закреплённое назначение проектов, а нормативное сравнение включает исходные версии proposal/design/tasks/specs.

Долговечный evidence хранить в приватном state плагина вне рабочего дерева с дедупликацией байтов и квотами на субъекта/change; предусмотреть восстановление после рестарта EDT. Объявлять гарантированный `retainUntil` при резервировании; по умолчанию проектировать окно 7 суток, с явным продлением до его истечения по политике стенда. Ни одно обещанное удержание не вытесняется новым. `ProjectCommitJournal` остаётся единственным автором результата confirm: добавить привязку change и удержание его recovery-записи **до** изменения ref. После потери ответа выдавать фактический терминальный receipt либо прежний recovery_required, не собирать вторую транзакцию по сообщению коммита.

### 4. Версионируемые документы отделить от работы оркестратора

Читать из серверного repo только допустимые типы существующего change: proposal/design/tasks/delta specs, review, iteration-log, metadata-plan, boundary/manifest и pre-pass exclusions. Для записи учитывать роль и вид операции: нормативные документы/человеческие решения нельзя изменять build-credential, для которого разрешены только отчёты, checkbox статуса или append служебного события. Для CAS сверять с фактическим WT под сериализацией writer’ов и защитой от внешней записи/замены, затем атомарно заменять редакцию. Если такое исключение гонки не обеспечено — отказ. Ключ append и его digest восстанавливаются вместе с записью. Изменение документа не означает индексацию: preview принимает только явно выбранные проверенные редакции того же repo, confirm повторяет их проверку.

Внешнее хранилище подходит для handoff, checkpoints и budgets клиента. Для документов, обязанных оказаться в Git-дереве кандидата, отдельный сервис потребовал бы протокола сверки двух источников истины. Поэтому в этом change — узкий адаптер серверного repo, а не файловый API или второй OpenSpec workspace. Для версионного ревью выбрано чтение с точными координатами: один набор серверных PASS не отвечает на незапланированный вопрос reviewer о caller или ассерте. Харнесс может обработать адресные документы в памяти, не копируя дерево; реализация его правил в EDT-MCP не требуется.

## Risks / Trade-offs

- **Широкий периметр vs конфиденциальность.** В смешанном repo выдавать полный approved scope либо явно reporting incomplete; denied не равносильно «совпадений нет».
- **Долгий build vs короткий plan.** Удерживать фактические входы до конца принятой job, не продлевать write grant. Для свежего плана сверка доказательства по manifest, а не по совпадению путей.
- **Стоимость больших конфигураций.** Ограничить поток/страницу и сканирование независимо; проверить реальный размер fixture. Ошибка бюджета безопаснее «полного» обрезанного отчёта.
- **Сбой между Git и квитанцией.** Fault-injection до/после обновления ref и индекса; ambiguity остаётся `recovery_required` даже при наличии предполагаемого SHA.

## Migration Plan

Поставлять новые формы вызовов и grants как opt-in, по умолчанию закрытые; миграция старых краткоживущих снимков в доказательства не поддерживается. Сначала включить чтение на тестовой ветке, затем isolated execution и evidence, в последнюю очередь права записи. Для отката прекратить приём новых build-планов, завершить/восстановить открытые journal entries и сохранить доступ к ранее обещанным receipts до конца retention. Проверить прежние схемы и поведение вызовов без новых параметров.
